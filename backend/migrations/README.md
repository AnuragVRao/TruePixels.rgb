# Database migrations (Alembic)

The schema is created and changed **only** here. The app does not create
tables at startup; it refuses to start unless the database is at the latest
revision (`app/shared/db.py`, `check_schema_current`).

Run from `backend/`; the target database is `DATABASE_URL` (backend/.env):

```bash
alembic upgrade head        # create or update the schema
alembic current             # which revision the database is at
alembic downgrade -1        # step back one revision
alembic downgrade base      # drop everything this history created
alembic revision --autogenerate -m "describe the change"   # new migration
```

**Two histories (2026-10-09).** `main`: `0001 … 0005 → 0006c → 0007` (both
recompute the stored confidence; 0007 restores the 2026-10-05 rule). Branch
`decision-map-1`:
`0001 … 0005 → 0006` (p_ai / certainty columns). The two are different
migrations with different ids on purpose. To move a database from one branch
to the other, check out the branch it is on, `alembic downgrade 0005`, then
switch branches and `alembic upgrade head`.

Every autogenerated migration is reviewed by hand before it is committed,
and `backend/tests/test_migrations.py` asserts the migrated schema equals the
SQLAlchemy models exactly, on SQLite and on PostgreSQL, so the two cannot
drift.

Ownership is unchanged by sharing one history: M1 owns D1 (users) and D2
(images), M2 owns D3 (models) and D4 (predictions), M3 owns D5
(explainability) and D6 (logs).

Case-insensitive email uniqueness uses a unique index on `lower(email)`
rather than the `citext` extension the original README suggested: it works
identically on SQLite and PostgreSQL and needs no extension.
